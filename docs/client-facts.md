## Transport (13)

- `PlaySoundFile(path)` readiness (empty file not ready, valid file ready, once-played cached): unverified — confirm in client. No declaration and no call site found in this `forever` clone (`grep -rn PlaySoundFile` over the full clone returns nothing); it is an engine-native function, documented only by the parent spec's `## Client behaviour facts` line, itself reported behaviour of this client rather than something derivable from Lua source. The in-client check this addon needs, before shipping: (1) poll an empty (0-byte) `.wav` repeatedly, then overwrite it with a valid `.wav` while still polling — confirm the empty-file result stays `false` on every poll and flips to `true` only after the valid write, never a stale `true` from a cached empty-file read; (2) repeat with the client's master sound and effects volume both at 0 and with `Sound_EnableAllSound` off, to confirm `PlaySoundFile`'s return value (not the audible result) still reflects file validity rather than the mute state; (3) once a poll returns `true` for a given path, confirm every later poll of that same path also returns `true` without re-reading the file (the "cached for the session" behaviour), including after this addon later overwrites that same path with a fresh empty file for the next `/reload` cycle. This addon (`ns.Transport.slotsLeft`/`pollNextSlot`, `Inbox.lua`) treats a `true` result as one-shot readiness and immediately requests `C_AddOns.LoadAddOn` for the matching slot, so a false positive here would double-deliver; a false negative would stall a delivery until the next poll tick.
- `holdMs` (documented in the parent's GameLink guarantee as "config; value written into `docs/client-facts.md` after the in-client measurement") cannot be read from `config.json` by the game addon, so this addon carries its own default, expressed in Lua as `Inbox.lua`'s `HOLD_CYCLES = 3` full repaint cycles at `REPAINT_INTERVAL_SECONDS = 0.25`, not as a millisecond constant: a queued `ask`/`items`/`cmd` message re-paints through every frame of its own pixel encoding, in order, for 3 full passes (so a 1-frame message holds for 3 × 0.25s = 0.75s; a 16-frame, 16 KB message holds for 3 × 16 × 0.25s = 12s) before this addon gives up on it and moves to the next queued message, ack or no ack. Expressing the hold as whole cycles rather than raw milliseconds keeps the guarantee proportional to message size, since a longer message already takes longer to paint every one of its frames once. `REPAINT_INTERVAL_SECONDS = 0.25` and `HOLD_CYCLES = 3` are this addon's own engineering choice, not a verified client fact, pending an in-client measurement of how many capture cycles the companion actually needs per frame at the maintainer's screen resolution and capture interval (`apps/companion/src/transport/screen-link.ts`'s `DEFAULT_POLL_INTERVAL_MS = 150`); if that measurement shows fewer or more capture attempts land per repaint tick than assumed here, `HOLD_CYCLES` is the value to change.
- D10 exemption for the codec's pixel cells: from `docs/specs/wow-companion-v1/06-codec.md:30` — "The codec cells use `SetColorTexture` with each channel exactly 0 or 1: they are the transport's data, not UI colour, so D10 does not apply to them." `SetColorTexture` itself: used e.g. `Interface/AddOns/Blizzard_UnitFrame/Shared/CompactUnitFrame.lua` (widely used core texture API, no single declaring Lua file in this generated-API clone).
- Slot addon loading: `C_AddOns.EnableAddOn(name)` then `C_AddOns.LoadAddOn(name)` (returns `loaded, message`), the same order Blizzard's own helper uses — `AddOnUtil.LoadAddOn`, `Interface/AddOns/Blizzard_SharedXMLBase/AddOnUtil.lua:29-31,40-49`. `EnableAddOn` before `LoadAddOn` because a `LoadOnDemand` addon must be enabled to load on some builds; this addon calls both unconditionally rather than checking prior enable state, since the 200 slot addons are private to this addon and never surfaced in the AddOns list UI.
- `C_Timer.After(seconds, callback)`: engine-native, no declaring Lua file in this clone; used e.g. `Interface/AddOns/Blizzard_Tutorials/Blizzard_Tutorials_Dracthyr.lua:124`. `Inbox.lua` uses it for both its repaint tick and its slot-poll tick, each re-scheduling itself recursively rather than using a repeating timer (no repeating-timer API is exposed to addons).
- Reply-slot and signal-file layout (this addon's own choice, not a client fact): `scripts/setup.ts` copies `addon/WoWCompanion/*.lua` and `WoWCompanion.toc` into `{wowPath}\Interface\AddOns\WoWCompanion\` (a real copy, not a directory junction — see "junction trap" below) and generates 200 sibling addon folders `{wowPath}\Interface\AddOns\WoWCompanion_R001\` .. `WoWCompanion_R200\`, each with a two-line `.toc` (`## Interface: 16001`, `## LoadOnDemand: 1`, `r.lua`) and an initially empty `r.lua`; `apps/companion/src/transport/slots.ts` overwrites `r.lua` with `WoWCompanion_Deliver(<session>, <literal>)` on delivery (two arguments: the addon's current session token, then the Lua table literal — see the hello/session paragraph below). Signal files live in a third sibling folder, `{wowPath}\Interface\AddOns\WoWCompanion_Signals\sig\001.wav`..`200.wav`, never inside `WoWCompanion\` itself. The `alive\` heartbeat folder from round 1 is dropped (PM decision 2026-09-27, round 2): nothing reads or writes it, `scripts/setup.ts` no longer generates it, and `status().connected` is derived from the hello/frame timing described below instead.
- Batching window (PM decision 2026-09-27, round 2): the companion cannot observe when the addon has actually read a delivered slot (`PlaySoundFile`'s cached-readiness behaviour gives the addon a one-bit signal, never a way to tell the companion back), so "batch everything queued since the last delivered slot" (parent `GameLink` guarantee) is implemented as a time hold rather than a true read-acknowledgement: after each signal flip, `createScreenLink` holds `pending` for `slotReadMs` (default 250 ms, `DEFAULT_SLOT_READ_MS` in `screen-link.ts`) before it will flush again, so every message queued in that window lands in the next slot together instead of each claiming its own slot. The default matches `Inbox.lua`'s own `REPAINT_INTERVAL_SECONDS = 0.25` s slot-poll cadence — the addon cannot notice a new slot faster than that anyway. `ScreenLinkConfig.delay`/`now` are injectable so tests can control the hold precisely (`apps/companion/test/transport/screen-link.test.ts`'s `link.batch` "holds messages sent after an await" case).
- Connection status (PM decision 2026-09-27, round 2): `GameLink.status().connected` is `true` once a `hello` has been decoded and a frame (any decoded frame, including a deduped repeat) was decoded within the last `connectedTimeoutMs` of `createScreenLink`'s `now()`; it is `false` before the first `hello` and again once that window elapses with no further frame. `connectedTimeoutMs` defaults to 5000 ms (`DEFAULT_CONNECTED_TIMEOUT_MS` in `apps/companion/src/transport/screen-link.ts`) — comfortably above the addon's own `REPAINT_INTERVAL_SECONDS = 0.25` s poll cadence and the companion's `DEFAULT_POLL_INTERVAL_MS = 150` ms capture cadence, so a few dropped or unsynced captures do not flip `connected` to `false`, while a genuinely closed game (window closed, capture stopped) is caught within one round of `holdMs`. This addon's own engineering choice, not a verified client fact; if capture proves slower or burstier in practice, `connectedTimeoutMs` is the value to change. `Codec.paint` leaves the last painted frame on screen between repaints (it only repaints on `C_Timer.After` ticks, never clears), so an idle game with nothing new to send still reads as connected as long as the last frame keeps getting re-captured.
- Junction trap (why the addon folder is copied, not junctioned): the mini-spec allowed either "install or junction the addon"; junctioning `{wowPath}\Interface\AddOns\WoWCompanion` to this repo's `addon/WoWCompanion/` would make that folder resolve to the tracked source tree, so any signal or slot file later written under it would land inside the git working tree instead of the game folder. `scripts/setup.ts` copies the addon's `.lua`/`.toc` files instead, and keeps every generated (untracked) file — the 200 slot addons and the `WoWCompanion_Signals` folder — in sibling folders under `AddOns\` that are never part of the repository, so nothing generated at setup or delivery time can be written into the git tree.
- `wowPath` (repeated from the Client section above): the flavour folder holding `WowB.exe`; `scripts/setup.ts` reads it from `config.json`'s `wowPath` field and refuses to run (prints an error, exits 1) rather than defaulting it when the field is absent, per D12/config discipline. `scripts/setup.test.ts` exercises `runSetup` directly against a temporary directory standing in for `wowPath`, never the real game folder.
- Hello handshake and slot-position sync (PM decision 2026-09-27, round 2 — supersedes the round-1 paragraph below): `Inbox.lua` paints `{t="hello", v=1, build, iface, session, slot=<its own next-slot index>}` at addon load and keeps repainting it (through the normal re-paint-until-acked path, `hello` is in `Inbox.lua`'s `ACKED_TYPES`) until the companion acks it — with no give-up, unlike `ask`/`items`/`cmd`'s `HOLD_CYCLES`, since the companion may start capturing after the addon has already loaded. If the addon's own `nextSlotIndex` changes while a hello is still unacked (for example, its slot-poll loop advances past stale slots left over from before this `/reload`), `Inbox.lua` re-encodes the hello with the new `slot` and a fresh `seq` rather than keep repainting the stale one. On the companion side, `createScreenLink` writes no outgoing slot at all before it has decoded a first `hello` (queued `send()` calls still return `ok`, they simply wait); once a `hello` is decoded, it sets its slot allocator to `hello.slot` (the wire value is 1-based, matching the addon's own `nextSlotIndex` and `WoWCompanion_Rnnn` naming; the allocator's internal index is 0-based, so the companion converts with `slot - 1` in one place, `handleHello` in `screen-link.ts`), empties every signal file at or after that position, and queues the ack for that hello so it lands in exactly that slot. `session` also changes on every `hello` whose token differs from the previous one, which clears the companion's frame-reassembly buffer (`frameBuf`) so a duplicate `seq` carried over from before the reload is never mistaken for a repeat of the new session's traffic (this pairs with `Inbox.lua`'s session token generator being reseeded — see below — and with `nextFrameSeq` starting from `math.random(0, 0xffff)` on each load instead of `time()`, so two sessions are very unlikely to share a starting `seq`). Together, both sides converge on the addon's real slot position after a `/reload` even when stale slots were passed while the hello was still in flight — this closes the round-1 "stale-session race" (previously tracked under `## Open work`); the remaining gap (a companion **restart** mid-session, where the addon has already acked its hello and has no reason to repaint it again) is not covered by this decision and is tracked below.
- Session token entropy (PM decision 2026-09-27, round 2): the round-1 token (`time()` seconds plus an unseeded `math.random`) could repeat across a `/reload` if the client does not itself reseed Lua's global RNG before addon code runs (unverified — no `math.randomseed` call site found anywhere in this `forever` clone; whether FrameXML seeds it before `OnLoad` fires is not established here). `Inbox.lua`'s session token now mixes three per-load-varying engine values — `GetServerTime()`, `debugprofilestop()` (sub-millisecond, monotonic since client start) and the fractional part of `GetTime()` — with `bit.bxor`/`bit.band`, each clamped to `0x7fffffff` before use (the same 32-bit signed-int cast that broke the round-1 `math.random(0, 0xffffffff)` call), then formats the mixed value alongside a `math.random(0, 0x7fffffff)` draw as `"%08x-%08x"`. `tests/lua/inbox_test.lua`'s `gen-r2-1` case proves the differentiation does not depend on `math.random` reseeding at all: it calls `math.randomseed(1)` before each of two simulated loads (the worst case, an RNG that resets identically on every reload) and confirms the sessions still differ from `debugprofilestop`/`GetTime` alone.
- Companion restart gap (sent to the PM 2026-09-27, round 2, not resolved by this slice): if the companion process restarts while the game is mid-session, the addon has already received and acked its `hello` and has no trigger to repaint it again, so the companion — which starts with no allocator position and no session — never learns the addon's real slot position and never writes another slot. Nothing in this slice's mini-spec covers a periodic addon-side hello re-announce or a companion-side reconnect probe; tracked in `HANDOFF-INTENT.md` under `## Open work` pending a PM protocol decision.
