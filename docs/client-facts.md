- Lua `bit` library 32-bit semantics: unverified — confirm in client: `/dump bit.bnot(0), bit.lshift(1,31)`. Until confirmed, every addon `bit` operation stays on operands and results below `2^31`, where the client's signed and unsigned interpretations agree; `tests/lua/bit_shim.lua` (this slice) implements unsigned 32-bit wraparound only over that range, no signed/unsigned branch above it, and enforces the constraint itself: it raises a Lua error whenever an operand or result would land at or above `2^31`, instead of silently returning an unverified value.

## Items and waypoint (07)

- Item stat call: `C_Item.GetItemInfo(itemId)` (13 returns: name, link, quality, itemLevel, requiredLevel, type, subType, stackCount, equipLoc, texture, sellPrice, classID, subclassID) — declared `Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua:626`, used e.g. `Interface/AddOns/Blizzard_ActionBar/WoWLabs/ActionButtonOverrides.lua:473`. Detailed stats: `C_Item.GetItemStats(itemLink)` — declared `Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua:1004` (no non-generated call site found in this clone; `ItemDetail.stats` is filled only from this call, never from QuestieDB, per D7). Uncached item retry: `C_Item.RequestLoadItemDataByID(itemId)` then the `ITEM_DATA_LOAD_RESULT` event (payload `itemID, success`) — declared `Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua:1857-1863`, wired `Interface/AddOns/Blizzard_ObjectAPI/Mainline/AsyncCallbackSystem.lua:18`. `ns.Items.details(ids, onDone)` is a callback, not a `→ ItemDetail[]` return — PM decision (gate round 1, 2026-09-27): item data loads asynchronously in the client (cache miss retried on `ITEM_DATA_LOAD_RESULT`, up to an 8s timeout), so a synchronous return is not achievable; `onDone(results)` runs exactly once, either synchronously when every id is already cached or asynchronously once every id resolves or the timeout elapses. Callers in slices 09/13 must use this callback shape, not the mini-spec's simplified synchronous signature. A single listener frame is created once at addon load (before any request can fire), keyed by a per-item pending-handler map, so registration always precedes `RequestLoadItemDataByID`; duplicate ids in one call are de-duplicated before requesting.
- Waypoint: unrestricted (no protected/combat-lockdown guard on either call) — `C_Map.CanSetUserWaypointOnMap(mapID)` then `C_Map.SetUserWaypoint(uiMapPoint)`, guarded exactly this way in `Interface/AddOns/Blizzard_SharedMapDataProviders/WaypointLocationDataProvider.lua:222-227` (slash-command handler, plain function call, no `securecall`/protected wrapper). `C_Map.SetUserWaypoint` returns `wasSet` (bool) — declared `Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua:608-611` — checked by this addon: `ns.Waypoint.set` returns `no_waypoint_map` and skips super-track when it is false, matching the same provider's own call-site check at line 227. Super-track: `C_SuperTrack.SetSuperTrackedUserWaypoint(true)` — same file, line 101. `UiMapPoint.CreateFromCoordinates(mapID, x, y)` takes fractional 0-1 coordinates — `Interface/AddOns/Blizzard_ObjectAPI/Mainline/UiMapPoint.lua:3`; this addon's `Waypoint = { x, y }` (parent spec) is 0-100, converted by `/100` before the call — this addon's own choice, not a client fact.
