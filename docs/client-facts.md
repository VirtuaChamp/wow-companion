## Transport (13)

- `PlaySoundFile(path)` answers whether the file exists, not whether it has content (in-client `/dump`, Forever 1.60.1, 2026-09-28): an existing file returns `true, handle`, an empty file included; a missing file returns nothing. The client only sees files that existed when it launched. For those, deleting the file makes the next call return nothing and re-creating it makes the next call return `true` again, live, without `/reload`. A file first created after launch is never seen until the client restarts. The earlier claim (empty file not ready, valid file ready, once-played cached) is wrong and is replaced by this one. Consequence, and this design: readiness is by presence, inverted from the first design. `scripts/setup.ts` creates every `sig/nnn.wav` (empty) before the client starts and says the client must be restarted after setup; a present file is not ready; the companion writes slot nnn's `r.lua` and then deletes `sig/nnn.wav`, which is the ready write; `Inbox.lua`'s `pollNextSlot` calls `PlaySoundFile(signal)` and calls `LoadAddOn` only when it returns nothing (file absent). The companion re-creates an empty signal file to empty a signal (a re-sync, or before reusing a slot) and never creates a signal path that setup did not create. The field failure the first design produced: every empty signal read as ready at once, the addon walked all 200 empty slots at login ("File ... r.lua is empty" error) and the companion then reported `slots_exhausted`. Tests: `tests/lua/inbox_test.lua` (field-bug block: every signal present, nothing written, no slot loaded) and `apps/companion/test/transport/two-sided.test.ts` ("field bug" case).
- Self-test files (PM addition 2026-09-28, fail closed): `scripts/setup.ts` also creates `sig/ctl-present.wav` and `sig/ctl-gone.wav` before launch. The companion deletes `ctl-gone.wav` at every start (missing file counts as done, any other failure is retried) before it writes any slot, and never re-creates it. `Inbox.lua` (`checkSignalsTrusted`) requires `PlaySoundFile(ctl-present)` to return `true` and `PlaySoundFile(ctl-gone)` to return nothing before it reads any slot. It runs the check at load, at every slot-poll tick and when the hello is acked; a tick-level re-check is what lets a game that started before the companion recover once `ctl-gone.wav` is deleted, because the ack that would trigger the other check reaches the addon only through a slot. `ctl-present` missing: the client cannot be trusted, one line is printed per load ("WoW Companion: reply signals not working on this client, restart the game after setup") and no slot is read. `ctl-gone` still present: the companion has not started since the client launched, the addon waits silently and keeps re-checking. The companion finds the folder of `ctl-gone.wav` from the folder of `paths.signalFile(0)` (`controlGoneFile` in `slots.ts`), so `bootstrap.ts` is unchanged.
- Placeholders and atomic writes (PM additions 2026-09-28): `scripts/setup.ts` writes each slot's `r.lua` as `WoWCompanion_Deliver(nil, nil)`, never an empty file; `WoWCompanion_Deliver` returns at once for a nil session or a non-table `msgs`, so loading a placeholder does nothing and raises nothing. `writeSlot` writes `r.lua.tmp` in the slot's folder, renames it over `r.lua` (`SlotFs.rename`), and only then deletes the signal file; the temp name is not in the slot's `.toc`, so the client never reads it. `Inbox.lua` calls `StopSound(handle)` on the handle `PlaySoundFile` returns for a present file, for slot probes and both control probes.
- The in-client re-test: re-run `pnpm run setup`, restart the client, `pnpm start`, `/ai hello`.
- `holdMs` (documented in the parent's GameLink guarantee as "config; value written into `docs/client-facts.md` after the in-client measurement") cannot be read from `config.json` by the game addon, and the addon no longer has a hold limit at all: a queued `ask`/`items`/`cmd` message repaints through every frame of its own pixel encoding, in order, for as many passes as it takes until its ack arrives, and the send queue advances only on that ack (no give-up after a number of passes; the earlier `HOLD_CYCLES` limit is gone). A frame is held at least `FRAME_HOLD_MIN_SECONDS = 0.2` and the repaint tick is `REPAINT_INTERVAL_SECONDS = 0.25`, this addon's own engineering choice, not a verified client fact, pending an in-client measurement of how many capture cycles the companion needs per frame at the maintainer's screen resolution and capture interval (`apps/companion/src/transport/screen-link.ts`'s `DEFAULT_POLL_INTERVAL_MS = 100`). A 1-frame message is on the line for 0.25 s per pass; a 16 KB message is 16 frames at 1024 payload bytes per frame (screens 1904 px wide and up), 4 s per pass, and 25 frames (6.25 s per pass) on a 1280 px wide screen where the frame payload is 673 bytes (frame count = ceil(bytes / payload per frame), see the Signal line section).
- D10 exemption for the codec's pixel cells: from `docs/specs/wow-companion-v1/06-codec.md:30` — "The codec cells use `SetColorTexture` with each channel exactly 0 or 1: they are the transport's data, not UI colour, so D10 does not apply to them." `SetColorTexture` itself: used e.g. `Interface/AddOns/Blizzard_UnitFrame/Shared/CompactUnitFrame.lua` (widely used core texture API, no single declaring Lua file in this generated-API clone).
- Slot addon loading: `C_AddOns.EnableAddOn(name)` then `C_AddOns.LoadAddOn(name)` (returns `loaded, message`), the same order Blizzard's own helper uses — `AddOnUtil.LoadAddOn`, `Interface/AddOns/Blizzard_SharedXMLBase/AddOnUtil.lua:29-31,40-49`. `EnableAddOn` before `LoadAddOn` because a `LoadOnDemand` addon must be enabled to load on some builds; this addon calls both unconditionally rather than checking prior enable state, since the 200 slot addons are private to this addon and never surfaced in the AddOns list UI.
- `C_Timer.After(seconds, callback)`: engine-native, no declaring Lua file in this clone; used e.g. `Interface/AddOns/Blizzard_Tutorials/Blizzard_Tutorials_Dracthyr.lua:124`. `Inbox.lua` uses it for both its repaint tick and its slot-poll tick, each re-scheduling itself recursively rather than using a repeating timer (no repeating-timer API is exposed to addons).
- Reply-slot and signal-file layout (this addon's own choice, not a client fact): `scripts/setup.ts` copies `addon/WoWCompanion/*.lua` and `WoWCompanion.toc` into `{wowPath}\Interface\AddOns\WoWCompanion\` (a real copy, not a directory junction — see "junction trap" below) and generates 200 sibling addon folders `{wowPath}\Interface\AddOns\WoWCompanion_R001\` .. `WoWCompanion_R200\`, each with a two-line `.toc` (`## Interface: 16001`, `## LoadOnDemand: 1`, `r.lua`) and an `r.lua` holding the placeholder `WoWCompanion_Deliver(nil, nil)`; `apps/companion/src/transport/slots.ts` overwrites `r.lua` with `WoWCompanion_Deliver(<session>, <literal>)` on delivery (two arguments: the addon's current session token, then the Lua table literal — see the hello/session paragraph below). Signal files live in a third sibling folder, `{wowPath}\Interface\AddOns\WoWCompanion_Signals\sig\001.wav`..`200.wav` (all created by setup, empty; present means not ready) plus `ctl-present.wav` and `ctl-gone.wav`, never inside `WoWCompanion\` itself. The `alive\` heartbeat folder from round 1 is dropped (PM decision 2026-09-27, round 2): nothing reads or writes it, `scripts/setup.ts` no longer generates it, and `status().connected` is derived from the hello/frame timing described below instead.
- Batching window (PM decision 2026-09-27, round 2): the companion cannot observe when the addon has actually read a delivered slot (`PlaySoundFile`'s file-presence behaviour gives the addon a one-bit signal, never a way to tell the companion back), so "batch everything queued since the last delivered slot" (parent `GameLink` guarantee) is implemented as a time hold rather than a true read-acknowledgement: after each signal delete, `createScreenLink` holds `pending` for `slotReadMs` (default 250 ms, `DEFAULT_SLOT_READ_MS` in `screen-link.ts`) before it will flush again, so every message queued in that window lands in the next slot together instead of each claiming its own slot. The default matches `Inbox.lua`'s own `REPAINT_INTERVAL_SECONDS = 0.25` s slot-poll cadence — the addon cannot notice a new slot faster than that anyway. `ScreenLinkConfig.delay`/`now` are injectable so tests can control the hold precisely (`apps/companion/test/transport/screen-link.test.ts`'s `link.batch` "holds messages sent after an await" case).
- Connection status (PM decision 2026-09-27, round 2, timeout revised with the signal line, 2026-09-29): `GameLink.status().connected` is `true` once a `hello` has been decoded and a frame (any decoded frame, including a deduped repeat) was decoded within the last `connectedTimeoutMs` of `createScreenLink`'s `now()`; it is `false` before the first `hello` and again once that window elapses with no further frame. The signal line is hidden while nothing is queued, so an idle game shows a frame only when the 10 s `again` hello blinks (`Inbox.lua`, one frame held at least 0.2 s); `connectedTimeoutMs` therefore defaults to 25000 ms (`DEFAULT_CONNECTED_TIMEOUT_MS` in `apps/companion/src/transport/screen-link.ts`), two announce periods plus the hold, and the capture interval is 100 ms (`DEFAULT_POLL_INTERVAL_MS`) so a 0.25 s blink is captured at least twice. This addon's own engineering choice, not a verified client fact; if capture proves slower or a blink is missed in practice, these two values are the ones to change. `Codec.hide` is called whenever the send queue is empty, so an idle game paints nothing.
- Junction trap (why the addon folder is copied, not junctioned): the mini-spec allowed either "install or junction the addon"; junctioning `{wowPath}\Interface\AddOns\WoWCompanion` to this repo's `addon/WoWCompanion/` would make that folder resolve to the tracked source tree, so any signal or slot file later written under it would land inside the git working tree instead of the game folder. `scripts/setup.ts` copies the addon's `.lua`/`.toc` files instead, and keeps every generated (untracked) file — the 200 slot addons and the `WoWCompanion_Signals` folder — in sibling folders under `AddOns\` that are never part of the repository, so nothing generated at setup or delivery time can be written into the git tree.
- `wowPath` (repeated from the Client section above): the flavour folder holding `WowB.exe`; `scripts/setup.ts` reads it from `config.json`'s `wowPath` field and refuses to run (prints an error, exits 1) rather than defaulting it when the field is absent, per D12/config discipline. `scripts/setup.test.ts` exercises `runSetup` directly against a temporary directory standing in for `wowPath`, never the real game folder.
- Hello handshake and slot-position sync — current account as of round 3 (PM decisions, specs `35f7c52`/`ff1a724`/`f03779c`; this paragraph replaces every earlier draft of it in this file's history): `Inbox.lua` paints `{t="hello", v=1, build, iface, session, slot=<its own next-slot index>}` at addon load and keeps repainting it (through the normal re-paint-until-acked path, `hello` is in `Inbox.lua`'s `ACKED_TYPES`) until the companion acks it — with no give-up, like `ask`/`items`/`cmd`, since the companion may start capturing after the addon has already loaded; every hello `seq` issued since the last ack is kept (`helloSeqsInFlight`), so an ack for an earlier attempt still stops the current (possibly rebuilt) hello. If the addon's own `nextSlotIndex` changes while a hello is still unacked, `Inbox.lua` re-encodes the hello with the new `slot` and a fresh `seq` rather than keep repainting the stale one. After the ack, `Inbox.lua` keeps re-announcing `hello` every `HELLO_INTERVAL_SECONDS` (10 s) with `again=true`, painted once and never held or acked (`announceHello`/`helloAnnounceTick`, skipped while one is already in flight). On the companion side, `createScreenLink` writes no outgoing slot at all before it has decoded a first `hello` (queued `send()` calls still return `ok`, they simply wait). A companion that holds no session (its own start, or a restart while the game keeps running) adopts the hello's session, empties no signal, and sets its allocator to the first slot at or after `hello.slot` (1-based on the wire, converted with `slot - 1` in `handleHello`) whose signal file is present, checking the signal files on disk through `SlotFs.exists` (a present file is not ready, so a slot whose `r.lua` was written but whose signal file is still present counts as free; an absent file is a reply written and not yet read and is passed over; an `exists` error is retried, never treated as free). Unread replies written by the previous process are therefore delivered by the addon in order, and nothing is written behind the addon even when the `again` hello it captured is stale (PM ruling, spec `4b888d4`). A companion that already holds a session re-syncs — moves its allocator to `hello.slot` and re-creates the empty signal file of every slot at or after that position — **only** when the hello's `session` differs from the one it holds, or `hello.slot` is ahead of the allocator's current position (`SlotAllocator.position()`); a same-session hello reporting a slot behind the allocator is just acked (a `slot` behind only means slots are written but not yet read by the addon — the normal steady state, not drift; re-syncing on it would roll the allocator backward over already-written, unread slots). An `again` hello is never acked, and without a re-sync it triggers no write at all, so an idle game uses zero slots for it. A signal reset that fails in any slot aborts the whole re-sync and is retried (`resetSignalsUntilEmpty`, every `slotReadMs`); nothing is written, released or re-queued into a slot until every required signal is empty, so a leftover ready signal can never let the addon pass a slot before its reply is written there. A position captured before a failed empty pass is never committed (the addon may have advanced while the retry ran): after the pass finally succeeds the re-sync stays open (`resyncing`, messages held, `emptiedAfterFailure`) until a hello observed after that pass names the position (a non-`again` hello still painted unacked is re-decoded from the same frame, since an unacked hello means the addon has not moved; an `again` hello needs a new frame), and only then are the ack written and the held messages released at that position. Every signal from the emptied floor up is empty, so the position needs no second pass. A genuine re-sync (new session, or slot ahead) writes exactly one slot holding only the ack of a non-`again` hello: anything queued before the hello, sent while the re-sync was in flight, or re-queued from earlier slots is held (`held`) and flushed only once a later frame from that session shows the ack was read (`awaitingPostAckFrame`, released by any decoded frame other than a non-`again` hello, since a rebuilt hello means the ack was not read; the client gives no direct read signal back). A re-sync triggered by an `again` hello queues no ack, so the held messages are released as soon as the signal reset finishes (a restarted companion sees only `again` hellos, because the addon already had its first hello acked by the previous companion; it takes the no-session path above). While a re-sync runs (`resyncing`) `scheduleFlush` starts nothing and `send()` goes to `held`, and `handleHello` awaits any flush already in flight before it moves the allocator, so no write can land at a position whose reset is still pending. On a new session the companion re-queues every non-ack message it wrote that no decoded hello has yet shown as read (PM ruling, spec `6aff4f8`): `written` keeps the slot each message went into, and a same-session hello (`again` or not) prunes the entries in slots below its `hello.slot`, since a slot below a `hello.slot` counts as read only when that hello came from the session the slot was written for; acks are dropped instead, since they reference a `seq` from a session the addon no longer recognises. A message the `/reload` stale-slot walk skipped (old session token) therefore comes back in the new session: delivery is at-least-once, not exactly-once (parent spec, PM decision 2026-09-28; a `reply`'s at-most-once handling by `id` is slice 09's responsibility, not this slice's). Duplicates are possible (slice 09 de-duplicates a `reply` by `id`). `frameBuf` is set to `{seq, complete: true}` (not cleared to `undefined`) on a new-session hello, so a repeated capture of that same hello frame is still deduplicated the normal way, while a session change still lets a genuinely different next frame through. `nextFrameSeq` is derived from the same per-load entropy mix as the session token (`bit.band(entropyMix, 0xffff)`, no `math.random` involved), so two sessions are very unlikely to share a starting `seq` even if the client does not reseed `math.random` between reloads. Together, both sides converge on the addon's real slot position after a `/reload`, a companion restart mid-session (within one `HELLO_INTERVAL_SECONDS`), and a failed slot write (the allocator only advances after the `r.lua` write, its rename and the signal delete all succeed, `slots.ts`'s `writeSlot`, so a retry reuses the same slot instead of leaving a hole); an allocator that hits `slots_exhausted` mid-flush stops retrying until the next re-sync instead of spinning. Tests: `apps/companion/test/transport/screen-link.test.ts`'s `link.hello`, `link.reannounce`, `link.atLeastOnce`, `link.exhausted` and `link.errors` describe blocks; `tests/lua/inbox_test.lua`'s hello-rebuild, hello-announce-timer and `LoadAddOn`-failure cases.
- Session token entropy (PM decision 2026-09-27, round 2, unchanged in round 3): the round-1 token (`time()` seconds plus an unseeded `math.random`) could repeat across a `/reload` if the client does not itself reseed Lua's global RNG before addon code runs (unverified — no `math.randomseed` call site found anywhere in this `forever` clone; whether FrameXML seeds it before `OnLoad` fires is not established here). `Inbox.lua`'s session token mixes three per-load-varying engine values — `GetServerTime()`, `debugprofilestop()` (sub-millisecond, monotonic since client start) and the fractional part of `GetTime()` — with `bit.bxor`/`bit.band`, each clamped to `0x7fffffff` before use (the same 32-bit signed-int cast that broke the round-1 `math.random(0, 0xffffffff)` call), then formats the mixed value alongside a `math.random(0, 0x7fffffff)` draw as `"%08x-%08x"`; the same mix (masked to 16 bits) seeds `nextFrameSeq`, with no `math.random` involved there at all. `tests/lua/inbox_test.lua`'s `gen-r2-1` case calls `math.randomseed(1)` before each of two simulated loads (the worst case, an RNG that resets identically on every reload) and confirms the session still differs from `debugprofilestop`/`GetTime` alone; a second case does the same for `nextFrameSeq`.
- Batching-window race and write sizing (P2/P3, round 3): `handleHello` awaits any in-flight `flushing` before moving the allocator, and a `resyncing` flag makes `scheduleFlush` refuse to start a new flush mid-re-sync, so a write can no longer land at a position whose empty-signal reset is still in progress. `send()`'s pre-check now sizes messages against a fixed maximum session length (`SESSION_LENGTH = 17`, the exact `"%08x-%08x"` format width, which `parseHello` in `packages/contracts` enforces as an upper bound on the `hello` session: 1 to 17 characters of `A-Za-z0-9_-`, so a flush can never find a message too large that `send()` accepted) instead of the live session string, so a message that was fine before the first `hello` cannot silently become `too_large` once the real (17-character) session is stamped in.

- Known limits of presence-based readiness (accepted by the user 2026-09-28, follow-up fix pending): after a `/reload`, signals of slots read in the previous session stay absent, so they read as ready and the pool does not refill until the companion re-creates them, and re-creating them while the addon polls can race; a companion stopped between renaming a slot's `r.lua` and deleting its signal can overwrite that delivery after its restart. Until the follow-up lands: after a `/reload` or when replies stop, re-run `node scripts/setup.ts` and restart the client.

### Signal line (game to companion, 2026-09-29)

- Geometry: the addon draws a thin line of coloured cells at the very top edge of the screen (setting "Signal line position": "Top edge" by default, or "Bottom edge", stored as `WoWCompanionDB.linePosition`; `ns.Transport.setLinePosition("top"|"bottom")` moves it at runtime, `Codec.setPosition` in `addon/WoWCompanion/Codec.lua`). Each cell is 1 physical pixel wide and 2 tall with a 1 pixel gap (pitch 2 px), rows are 2 px tall with no gap, at most 3 rows, anchored to the top-left (or bottom-left) corner of `UIParent`. Cells are one of 8 pure colours (each channel 0 or 1 through `SetColorTexture`), 3 bits per cell; a black cell is simply not drawn over the solid black backing texture, which exists only while the line shows.
- Counter-scale: the frame calls `SetScale(1 / UIParent:GetEffectiveScale())` and sizes cells and rows in `PixelUtil.GetPixelToUIUnitFactor()` units (called in `applyLayout` of `Codec.lua`), `768 / physicalHeight` (`Interface/AddOns/Blizzard_SharedXML/PixelUtil.lua:3-6`, physical size from `GetPhysicalScreenSize`, documented at `Interface/AddOns/Blizzard_APIDocumentationGenerated/ScreenDocumentation.lua:19`), so one cell is exactly one physical pixel whatever the UI scale. The scale call alone leaves a unit at `physicalHeight / 768` pixels, which is why the factor is needed. Geometry is re-applied on `UI_SCALE_CHANGED` (`Interface/AddOns/Blizzard_APIDocumentationGenerated/UIManagerDocumentation.lua:91`) and `DISPLAY_SIZE_CHANGED` (`Interface/AddOns/Blizzard_APIDocumentationGenerated/VideoDocumentation.lua:137`); the event frame stays registered while the line is hidden.
- Row layout: every row is `anchor (12 cells, fixed non-black pattern) | count (4 cells, base 8, the number of data cells in the row) | data cells`. The row holds `floor((physicalWidth - 32) / 2)` cells; the line starts at x = 0 of `UIParent` and keeps 32 px of slack on the right. Data cells per row: 928 at 1920 wide, 1248 at 2560 wide (1920: 348 bytes per row, 1044 per 3-row frame; 2560: 468 bytes per row, 1404 per frame). The payload per frame is `min(1024, capacity - 11)`: 1024 bytes from 1904 px wide up (so 1920 and 2560 both carry 1024 per frame), 853 at 1600, 673 at 1280, 515 at 1000, and a message needing more than 255 frames is refused (`too_large`) because the frame count is one byte. Frames for a 16 KB message: 16 at 1024, 20 at 853, 25 at 673. The frame header is unchanged (`magic 0x57 0x43`, version, seq, total, index, length, payload, crc16-CCITT), the codec version is 2. A decoded frame of another codec version counts as a bad frame and logs the versions-differ line (below).
- When the line shows: only while the send queue is non-empty. Each frame is held at least 0.2 s (`FRAME_HOLD_MIN_SECONDS`; the repaint tick is 0.25 s), acked types (`ask`, `items`, `cmd`, `hello`) repaint until acked, then the line and its backing are hidden. The 10 s `again` hello therefore blinks for 0.25 s; a state delta paints only when it changes; a full snapshot of F frames keeps the line visible for F x 0.25 s: F is ceil(bytes / payload per frame), at most 16 frames (4 s) on screens 1904 px wide and up for the 16 KB maximum, 25 frames (6.25 s) at 1280 wide; a message that needs an ack (`ask`, `items`, `cmd`) repaints its frames, pass after pass, until its ack arrives, and the queue behind it waits: it is never given up. After 30 s without an ack the addon says once, in the Claude window when the module is loaded as "[Claude] the companion isn't answering; your message is still waiting." and otherwise as the chat line "WoW Companion: the companion isn't answering; your message is still waiting."; a `cmd` or `items` send that meets the full queue (8 entries) shows "[Claude] busy, not sent" in the window or "WoW Companion: busy, not sent" in chat instead of vanishing. A message that no longer fits three rows after a resolution change is re-encoded with a fresh `seq` for the new width (an ack naming either `seq` clears it), and dropped with one printed line when it still does not fit, "WoW Companion: <your question | a chat command | item details | some game data | a message> was not sent, it is too large for the signal line at this screen size" (once per kind), the one case where an `ask`, `cmd` or `items` message is lost, by design and never silently. The 10 s `again` hello is a pending flag, never a queue entry, so it cannot sit behind anything: with nothing on the line it paints at once; while an acked message (`ask`, `cmd`, `items`) is current it paints once at the message's next pass boundary, after a complete uninterrupted pass of all its frames, and the message then resumes from frame 1 for its next full pass (a 16 KB message at 800 px is 41 frames and a pass longer than the hello interval, so a hello never cuts into a pass); while a `state` or another one-pass message is current it paints between that message and the next queued one. A companion restarted while a message waits therefore learns the session from that hello, re-syncs and acks the waiting message without a `/reload`. The companion keeps the partial frames of a multi-frame message in a buffer separate from the one that de-duplicates single-frame messages, so a hello between two passes does not discard them. Delivery of `ask` and `cmd` is at-least-once, never lossy: an `ask` is delivered once by its id across re-encoded seqs and a `cmd` carries an id minted by the addon like an ask id; `items` is idempotent by its `req`. The companion remembers the last 500 ask and cmd ids in `apps/companion/state/handled-ids.json` (gitignored, written atomically; a missing file is empty, a malformed one stops the companion at start). The link delivers an ask or cmd without acking it, the daemon applies it and saves the chats and settings state, then calls `link.committed(msg)`, which records the id in the file and only then writes the ack (every seq seen for that id, so a re-encoded copy is acked too, and a second seq that arrives while the first is still being applied is not delivered). A message whose id is already recorded is acked again and not delivered. A crash after receipt but before the effect is saved leaves nothing acked, so the addon repaints it and it is applied once; a crash after the effect is saved but before the id is recorded applies it a second time (the accepted at-least-once cost, a duplicate `new` chat for example, never a lost message); a failed state or id write holds the ack and is retried every second. A message the daemon refuses (busy, unknown chat) is committed too so the addon stops repainting it, but an unexpected exception while applying one is not committed: the daemon releases the link's reservation and reassembly state (`link.release`) so the addon's repaint redelivers it, counts failures per id, and after the third failure sends the addon an `error` (code `daemon_error`, with the message id and chat, shown as "the companion could not handle that message; try again.") and commits it so nothing loops forever. Every pending ack is bound to the session it arrived in: a new-session hello drops the old ones synchronously, before its first await (signal reset), and the slot writer drops any ack whose session is not the current one at write time, so no interleaving can leak one; a commit that finishes after the session changed still records the id but queues no ack, so an ack never lands in a newer session where a reused 16-bit seq could clear an unrelated message. While `ctl-gone.wav` is still present (the companion has not started since this client launched, or `ctl-present.wav` is missing) nothing is painted at all, not even the first `hello`; the addon checks on its 0.25 s poll tick and paints the `hello` on the tick that sees `ctl-gone.wav` gone. With the companion running the first `hello` repaints on every tick until acked; if it is still unacked 20 s after the companion was first seen running, the two warning lines are printed once ("WoW Companion: can't read its signal line. Show the interface (Alt+Z) if it is hidden." and "WoW Companion: turn off anti-aliasing and screen overlays and set render scale to 100% in Options > Graphics, or move the line in Options > AddOns > WoW Companion.") and the `hello` goes dormant (line hidden), blinking once at each 10 s `again` tick until acked, after which the addon returns to normal.
- Reader (`apps/companion/src/transport/capture.ts`, `line-reader.ts`): a persistent PowerShell child captures, per request, an 8 row strip (three 2 px rows plus 2 px of slack) at the top of the client area and one at the bottom, full client width (`GetClientRect` and `ClientToScreen`, `CopyFromScreen`, after `SetProcessDPIAware`), and answers with an 8 byte header (magic `WCL1` and the width, checked against 0 to 16384; anything else counts as out of step and respawns the child) followed by both strips. The reader collects every anchor match at any x offset on both strips (the edge it last read first), samples each cell at its centre on both pixel rows of its row, and accepts a candidate only when its frame decodes: a capture whose frame passes the CRC is accepted as it is, and game pixels that happen to match the anchor never hide the real line. Only when no single capture decodes does it take the most frequent value per cell across recent captures of the same image, and it keeps one independent tally per candidate position: a candidate is accepted as soon as its own tally decodes, so a persistent decoy can never starve the real line (a header that carries the magic bytes only decides which failure is reported when none decodes). Two captures count as the same image when they differ in at most 2 cells over the cells that carry data (padding is ignored); otherwise the tally restarts with the newest capture, so a new frame is never outvoted by an old one. The pitch is fixed at 2 px: an encoded row always fills the screen width at that pitch, so a larger pitch could not fit real frames and is not attempted. A 1 px cell drawn 2 px wide covers only its gap, so the centre sample stays right. A capture that shows no line but carries the version 1 grid is recognised and logs the versions-differ line once: the full 126-cell sync row (cell i is colour i mod 8) in solid 4 x 4 px blocks at the top-left, followed by two row-count cells that read 1 to 63 rows, so a normal top-edge pattern that matches a prefix is not reported.
- Video settings that break reading: anti-aliasing (blends the cell edge into the gap and the backing), a render scale other than 100% (the line is resampled and the pitch is no longer an integer), screen filters or overlays (Discord, GeForce and Steam overlays, colour filters), and f.lux or other colour shifting (the pure colours are no longer pure). `Inbox.lua` prints two short chat lines, both with the addon's one chat prefix "WoW Companion: ", when the companion has been running for 20 s (`ctl-gone.wav` absent) and the first `hello` has been unacked for 20 s (`UNREADABLE_LINE_AFTER_SECONDS`, both clocks), once per load, reset when a hello is acked: "WoW Companion: can't read its signal line. Show the interface (Alt+Z) if it is hidden." and "WoW Companion: turn off anti-aliasing and screen overlays and set render scale to 100% in Options > Graphics, or move the line in Options > AddOns > WoW Companion." No chat line names an internal message or type (a message too large for the line is reported as "your question", "a chat command", "item details" or "some game data"); the stall and busy notices go through the Claude window as "[Claude] ..." or, without the window, as a prefixed chat line. The companion only logs, rate limited to one line per 30 s, when it sees the line but no frame decodes, and logs once "addon and companion versions differ, run setup and restart the game" when frames decode but carry another codec version or the capture shows the version 1 grid. The reverse mismatch (new addon, old companion) is silent on the companion side, because the old companion cannot read the new line at all; the new addon then prints its two lines after 20 s, and the remedy is the same: run setup and restart both.

## Build-db (05)

- Skip rule (PM, 2026-09-28): a source row that cannot satisfy the schema (empty or missing name, missing or non-integer id, missing or non-finite coordinate, an item source kind outside the four allowed) is skipped, never repaired with an invented value. Children of a skipped row are skipped with it: spawns of a skipped npc or object, quest start and end links and item sources whose owner is skipped.
- A polymorphic link (quest start and end, item source) survives only when its target id is a kept row of the matching kind (npc, object, item or quest); a target that is absent from the source and a target that was skipped are treated alike, and the link is dropped and counted as skipped in its own table. A link of an unknown kind is dropped.
- A nullable single reference to another row (`quest.next_in_chain`) that names a quest that is not kept is set to null, never replaced with an invented value and never cascaded to the quest that holds it. The build reports the number of such references and the first source ids under the field name; they are not counted in the skip cap, since the row itself is kept. The other cross-row columns are the spawn and link owner ids above; `zone_or_sort`, `zone_id` and `faction_id` name no table in this database.
- The build prints, per table, the source row count, the skipped count and the first five source ids (for a child table, the owner id), then the nulled references. It fails closed on a missing file, an unreadable table, a table with zero source rows, or more than 2% of a table's source rows skipped (children and dropped links included), naming the table and the first ids. The 2% limit is `MAX_SKIPPED_PERCENT` in `scripts/build-db/sanitize.ts` (PM ruling 2026-09-28: it catches structural breakage, and a row without a name cannot be searched); `buildDb` and the CLI always use it, and `sanitizeExportedData` accepts only a finite non-negative override for tests.
- The counts of a real run are printed by the build itself at run time; none are recorded here.

## Taint from the shared StaticPopup (chat-redesign, 2026-09-29)

Source: the client's taint log, saved as `.claude/output/spec/01-wow-companion-v1/taint-2026-09-29.log` (172 lines, 8 taint reports, all the same field). Every "An action was blocked because of taint from WoWCompanion" (`SpellStopCasting`, `SpellStopTargeting`) is reached from `TOGGLEGAMEMENU` (Esc) through `Interface/AddOns/Blizzard_GameMenuEsc/Blizzard_GameMenuEsc.lua:101` (`TryHandleGameMenuEsc`) and starts with "Execution tainted by WoWCompanion while reading field heightPadding" at `Interface/AddOns/Blizzard_SharedXML/LayoutFrame.lua:166` (`StaticPopup1:GetHeightPadding()`), called from `LayoutFrame.lua:518` (`Layout`), `Interface/AddOns/Blizzard_StaticPopup_Game/GameDialog.lua:698` (`Resize`) and `Interface/AddOns/Blizzard_StaticPopup/StaticPopup.lua:424` (`StaticPopup_Show`). ## Waypoint offered, never set automatically (chat-redesign, 2026-09-29, ADR 0001, PM ruling)

A reply that carries a waypoint no longer calls `ns.Waypoint.set` (`C_Map.SetUserWaypoint` and `C_SuperTrack.SetSuperTrackedUserWaypoint`, see "Items and waypoint (07)") by itself: `AiWindow.onReply` keeps the waypoint on the reply's entry and adds a grey line "waypoint: <label> (x, y) [Set waypoint]" whose `[Set waypoint]` is an `addon` hyperlink (`LinkUtil.FormatLink(LinkTypes.AddOn, ...)`, same route as `[open]`, `Interface/AddOns/Blizzard_SharedXML/LinkUtil.lua:69-77`, dispatched through `EventRegistry` `SetItemRef`). Only the player's click on that link calls `ns.Waypoint.set` with the stored map, coordinates and label, and a grey line confirms or names the refusal. The waypoint stays on the entry, so the line reappears from the per-chat cache and when a `history` (which carries no waypoints) replaces the cache; offers are kept for the 400 most recent replies (addon bound, not a client fact). The companion's system prompt says a waypoint is only offered as a button (`WAYPOINT_RULE`, `core/prompt.ts`). The MCP tool description in `apps/mcp/src/server.ts` now reads "Offer a map waypoint to the player ... it is set only when the player clicks it".
