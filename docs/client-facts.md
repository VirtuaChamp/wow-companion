## Settings and report (10)

- Settings category: `Settings.RegisterVerticalLayoutCategory(name)` — `Interface/AddOns/Blizzard_Settings_Shared/Blizzard_Settings.lua:154` — returns a `SettingsCategoryMixin` with `:GetID()` (`Interface/AddOns/Blizzard_Settings_Shared/Blizzard_Category.lua:13`) — then `Settings.RegisterAddOnCategory(category)` — same file, line 134 — registers it under Options > AddOns; `Settings.OpenToCategory(categoryID, scrollToElementName)` — same file, line 144, forwarded to `C_SettingsUtil.OpenSettingsPanel(categoryID)` — takes the numeric category id, not the category table (this addon calls `Settings.OpenToCategory(category:GetID())`). The category is registered once at addon load, not lazily on first open. Confirmed present in this `forever` clone; real "Options > AddOns > WoW Companion" navigation is unverified — confirm in client.
- Proxy settings (this addon has no CVar to bind to, values live in `ns.Settings` state instead): `Settings.RegisterProxySetting(category, variable, varType, name, defaultValue, getValue, setValue)` — same file, line 178.
- Dropdown controls: `Settings.CreateDropdown(category, setting, options, tooltip)` — same file, line 410. `Settings.CreateDropdownOptionInserter` (same file, lines 513-543) only builds an entry when `optionData.controlType == Settings.ControlType.Radio`; anything else hits `assertsafe(false, "Unhandled control type")` and the dropdown stays empty. Every `options` function on this addon therefore returns `Settings.CreateControlTextContainer():GetData()` — the container's `:Add(value, label, tooltip)` (`SettingsControlTextContainerMixin:Add`, same file, lines 249-252) stamps `controlType = Settings.ControlType.Radio` on every entry; a plain `{value, label, tooltip}` table (no `controlType`) is not accepted.
- Per-option disabled entry with a reason shown as the option's tooltip: the tooltip renderer (`Settings.CreateOptionsInitTooltip`, same file, lines 415-462) reads `option.tooltip` for the reason text and prints `option.disabled` itself as the tooltip's error line (`GameTooltip_AddErrorLine(SettingsTooltip, option.disabled)`, line 458) — `option.disabled` must be the reason string, not a boolean, or the tooltip prints a boolean where text is expected. `Settings.CreateDropdownButton` (same file, lines 494-498) builds the radio entry from `optionData.label`/`isSelected`/`setSelected` only — it never reads `optionData.disabled`, so it does not grey out or refuse a click on a disabled entry by itself (this is a real gap against the parent spec's "shown disabled" UX bullet, tracked as `ui-r2-4`/INFO — platform-standard, mirrored by Blizzard's own locale dropdown below). A separate field, `option.disabledReason`, does exist on real Blizzard option tables — `Interface/AddOns/Blizzard_Settings_Shared/Blizzard_Settings_PreferredPlaySettings.lua:65-66,83-84` sets it alongside `option.disabled = true` (a boolean, not a string, in that caller) — but `CreateOptionsInitTooltip` never reads `disabledReason`; a repo-wide grep confirms no reader exists anywhere in `Blizzard_Settings_Shared` or `Blizzard_Menu`. This addon sets both `option.tooltip = reason` and `option.disabled = reason` (the reason string, matching what the tooltip renderer actually consumes, not the `PreferredPlaySettings.lua` shape) on a container entry for an uninstalled/disabled provider, a usable provider with no models listed (`aca-r2-4`), or an unavailable "This chat only" scope, and additionally refuses the value in `ns.Settings.set*` so a stale selection cannot be sent even if the client ever allowed the click.
- Whole-control enable/disable, and why a plain `Settings.NotifyUpdate(variable)` alone does not refresh an already-open control: `initializer:AddModifyPredicate(fn)` / `initializer:EvaluateModifyPredicates()` — `Interface/AddOns/Blizzard_Settings_Shared/Blizzard_SettingControls.lua:137,148`; the control reads this through `SettingsControlMixin:IsEnabled()` (line 543). `EvaluateState()` (which actually calls `IsEnabled()`/`EvaluateModifyPredicates()` and redraws the control) runs only at the control's own `Init` (line 311) or when a _parent_ setting's value changes (`SettingsListElementMixin:Init` wires `OnParentSettingValueChanged` to the parent setting's value-changed callback at lines 315-321; `OnParentSettingValueChanged` calls `EvaluateState()` at lines 370-372). `Settings.NotifyUpdate(variable)` (`Blizzard_Settings.lua:206`) only reaches `SettingMixin:NotifyUpdate()` → `TriggerValueChanged` → the control's own `OnSettingValueChanged` → `SetValue` (`Blizzard_SettingControls.lua:532-534` for the base control, `888-899` for a dropdown's `InitDropdown`, `623-643` for a checkbox's `OnSettingValueChanged`/`SetValue` (`PlaySound` at 637-643)) — it never calls `EvaluateState` on the notified control itself. `initializer:AddEvaluateStateCVar(cvar)` (`Blizzard_SettingControls.lua:175`, wired the same way at lines 330-335 — `self.cbrHandles:SetOnValueChangedCallback(cvar, self.EvaluateState, self)`) is what wires a control to re-run `EvaluateState` when a named variable's value changes — both this and the parent-setting wiring above go through the same generic, string-keyed `SettingsCallbackRegistry` (`Blizzard_Settings.lua:665,696`; `SettingMixin:TriggerValueChanged` fires `SettingsCallbackRegistry:TriggerEvent(self.variable, ...)`), so a `cvar` name here is any registered setting's own variable, not necessarily a real engine CVar. This addon registers one hidden proxy setting (`WOWC_HUB`, `RegisterProxySetting` only — no `CreateDropdown`/`CreateCheckbox`, so it has no control and never appears in the panel; `Settings.GetSetting`/`NotifyUpdate` only need the setting registered, not displayed — `Blizzard_Settings.lua:202-210`) and calls `initializer:AddEvaluateStateCVar("WOWC_HUB")` on all four real controls (provider/model/effort/scope), so `Settings.NotifyUpdate("WOWC_HUB")` alone forces every one of them to re-run `EvaluateState` after any state change, closing the "stays greyed until the user leaves and re-enters the category" gap, with no layout side effect (an earlier draft parented the controls to each other via `SetParentInitializer`, which forces the child row into an indented, smaller font — lines 225,337 — this design avoids that entirely). Model, effort and the scope checkbox's own `Settings.NotifyUpdate` (dropdown `InitDropdown` or checkbox `SetValue` → `PlaySound(SOUNDKIT.IG_MAINMENU_OPTION_CHECKBOX_ON/OFF)`, lines 637-643) are only called when that variable's own displayed value actually changed, so an unrelated change never plays the checkbox's click sound.
- Report dialog frame: `CreateFrame("Frame", name, UIParent, "BasicFrameTemplateWithInset")` — template declared `Interface/AddOns/Blizzard_UIPanelTemplates/Mainline/UIPanelTemplates.xml:602`, inheriting `BasicFrameTemplate` → `BaseBasicFrameTemplate`, which already declares `<Button parentKey="CloseButton" inherits="UIPanelCloseButtonDefaultAnchors"/>` in its own `<Frames>` block (same file, line 571) and a `parentKey="TitleText"` FontString (line 533) — this addon reuses `frame.CloseButton`/`frame.TitleText` rather than creating a second close button, and adds its own `frame.Instructions` FontString above the box ("Copy this into a new GitHub issue:", `ui-r2-5`) matching Blizzard's own export/share-code dialog convention of pairing a scroll box with a caption. `WoWCompanionReportFrame` is a named, addon-created frame (allowed by the parent spec's Code shape exception for `WoWCompanion*`-named frames that must join `UISpecialFrames`); naming it does not itself write a Lua global assignment the source has to declare, since WoW's frame system — not this addon's code — is what binds the name.
- The scrollable box uses the `InputScrollFrameTemplate` scroll frame — `Interface/AddOns/Blizzard_SharedXML/Shared/InputBox/InputBoxTemplates.xml:72`, backed by `InputScrollFrame_OnLoad` (`Interface/AddOns/Blizzard_SharedXML/Shared/InputBox/InputBoxTemplates.lua:80-90`) — whose `<ScrollChild>` already declares `parentKey="EditBox"` (XML file, line 150); this addon reads `frame.ScrollFrame.EditBox` rather than creating a second one. `InputScrollFrame_OnLoad` _does_ resize the `EditBox` itself (`self.EditBox:SetWidth(self:GetWidth() - 18)`, `InputBoxTemplates.lua:87`) and sets `self.CharCount:SetShown(not self.hideCharCount)` (line 90, `self.hideCharCount` is `nil`/false by default) and `self.EditBox:SetMaxLetters(self.maxLetters)` (line 88, `nil` by default) — but that `OnLoad` runs during `CreateFrame`, before this addon calls `:SetSize(...)` on the `ScrollFrame` (`GetWidth()` is still its pre-layout value at that point), and there is no Lua-side way to set `hideCharCount`/`maxLetters` before a plain `CreateFrame` call runs the template's `OnLoad`. So this addon corrects both after creation: `frame.ScrollFrame.CharCount:Hide()` once (permanent — `InputScrollFrame_OnTextChanged`, `InputBoxTemplates.lua:104-115`, only calls `CharCount:SetText(...)`, never `:Show()`, so a manual `Hide()` sticks) and `editBox:SetWidth(frame.ScrollFrame:GetWidth() - 18)` with the correct scrollbar allowance, once the `ScrollFrame`'s real size is set. Read-only is this addon's own choice (D2, written from scratch): `EditBox:HookScript("OnTextChanged", ...)` composes with (rather than replacing) the template's own `InputScrollFrame_OnTextChanged`/`InputScrollFrame_OnEscapePressed` scroll-range handling and reverts any change back to the built report text — no client-provided read-only flag exists on `EditBox`. The frame's name is added to `UISpecialFrames` (global table declared `Interface/AddOns/Blizzard_UIParentPanelManager/Shared/UIParentPanelManager.lua:21`, read on every `ESCAPE` keypress at line 1108) so Escape closes it, the standard convention for a dialog frame.
- Client build for the report box: `GetBuildInfo()` (native API, not defined in Lua source; usage confirmed e.g. `Interface/AddOns/Blizzard_GlueXML/Mainline/AccountLogin.lua:25`, `local version, internalVersion, date, _, versionType, buildType = GetBuildInfo();`) returns `version, build, date, tocversion, ...`; this addon reads `version` and `build` (matches `## Interface: 16001` / build `1.60.1.70009` recorded under `## Client` above).
- Addon version for the report box: `C_AddOns.GetAddOnMetadata(name, "Version")` (native API, not defined in Lua source; usage confirmed e.g. `Interface/AddOns/Blizzard_AddOnList/AddonList.lua:390`, called there with an addon index rather than a name — both forms are the documented signature). The addon name is read from the file's own vararg (`local addonName, ns = ...`, the name WoW passes to every addon file), not hardcoded.
- Companion version for the report box: settled by the PM (2026-09-27, spec commit `15e90de`): `packages/contracts`' `options` message carries an optional `companionVersion?: string` field. `ns.Settings.onOptions(msg)` forwards `msg.companionVersion` to `ns.Report.setCompanionVersion(v)` when present; until the companion process sends it, the report box prints `Companion version: unknown`.
- Provider/model/effort for the report box: reused from `ns.Settings.current()`, which now returns the currently _displayed_ choice — the active chat's own choice (`options.chat`) when the "This chat only" checkbox is checked and one exists, otherwise the global choice (`options.active`); never an unconfirmed, locally-picked value. No character name, realm or account path is read or included anywhere in `Report.lua` (AC 20) — confirmed by loading the real `State.lua` in `report_box_test.lua` and asserting its character fixture's name never appears in the built report text, since `Report.lua` never reads `ns.State` at all.
- Options message shape (spec commit `6972670`, PM decision 2026-09-27, superseding round-0/1's `defaultProvider`): `{t:"options"}` carries `active: Choice` (the global provider/model/effort) and an optional `chat?: {id: string} & Choice` (the active chat's own choice, when it has one); `Choice = {provider, model, effort?}`. A dropdown change sends `{t:"settings"}` immediately and is _pending_ — the displayed choice (read only through `ns.Settings.current()`) is set only from `active`/`chat` on the next `options` message, never optimistically from the user's own click. When that `options` message's `active` (or `chat`, if the pending change was chat-scoped) matches the pending choice field-for-field, this addon prints `[Claude] now using <provider> · <model> · <effort>` through `ns.AiWindow.notice(text)` (slice 09's module, called directly per the TOC load order — `AiWindow.lua` loads before `Settings.lua`); `<effort>` reads `unknown` when the choice carries no effort, matching the report box's own placeholder for the same field. A non-matching `options` message still updates the displayed `active`/`chat` but leaves the pending change open (PM decision) until a later matching `options`, an `{t:"error"}`, or a newer dropdown change replaces it. `ns.Settings.onError(msg)`, called by slice 09's `Core.lua` dispatcher on a `{t:"error"}` message while a change is pending, clears the pending change and prints the companion's own `message` the same way (AC 17's "previous settings kept" refusal). The "This chat only" checkbox itself sends nothing (`aca-r2-3`): checking or unchecking it only changes which of `active`/`chat` the dropdowns display and which choice the next dropdown change is sent against (with a `chat: <active chat id>` field on the outgoing `{t:"settings"}` message when checked).
- Cross-slice dispatch (PM decision, 2026-09-27): this addon never subscribes itself to `ns.Transport.onMessage`. It exposes `ns.Settings.onOptions(msg)`, `ns.Settings.onChats(msg)` and `ns.Settings.onError(msg)` for slice 09's `Core.lua` (owns the single `ns.Transport.onMessage` dispatch by `t`) to call. The "This chat only" checkbox's _availability_ (distinct from which choice it shows) tracks the active chat id from the last `{t:"chats"}` message's `active` field (`packages/contracts/src/types.ts`) via `ns.Settings.onChats`, and refuses to check until one is known.
