D14 status, round 2 (2026-09-27): the PM's live probes (`no-shell-probe.txt`) confirm D14 is closed for codex, not an accepted gap — `--disable shell_tool` removes the shell tool from the model's toolset entirely (Probe A/B: `CANNOT_READ`, no shell or file-reading tool reachable, `marker.txt` unchanged) versus the control run (`shell_tool` enabled), which still had a shell tool, only sandbox-blocked. `DISABLED_FEATURES` in `codex.ts` grew eight more names (`code_mode_host`, `unified_exec`, `unified_exec_tty`, `multi_agent`, `view_image`, `image_generation`, `memories`, `goals`) per Probe B. `codex describe()` ships `enabled: true` by default; no `allowReadOnlyShell` gate.

D14 status, round 2-r2 (2026-09-27): `code_mode_host` removed from `DISABLED_FEATURES`. A live run through the adapter's own `run()` (model `gpt-5.6-sol`) showed codex routes every tool call, MCP included, through the code-mode host in this version — disabling it made codex "fail closed" (`Code Mode is unavailable because code-mode host is disabled ... enable features.code_mode_host`) and answer `pong` without ever calling `wowc_ping`, and it also made the D14 write-attempt proof vacuous (`apply_patch` could not be called either). Re-reading Probe A above: it already had `code_mode_host` enabled and codex still reported `CANNOT_READ` on `marker.txt` (its JS runner has no filesystem access) — `code_mode_host` was never load-bearing for the D14 no-file-write finding, only `shell_tool` (and the rest of Probe B's set) was. `DISABLED_FEATURES` is now sixteen names; `shell_tool` and Probe B's other seven additions are unchanged.

D14 status, round 2-r2 final (2026-09-27): the write-attempt proof landed. `write-attempt.jsonl`/`write-attempt-result.json` (row above) record a real `apply_patch` call rejected by the read-only sandbox, `marker.txt` byte-identical afterward. `provider.codex.d14 write-attempt: the marker is unchanged and codex reports the sandbox rejection` in `provider.codex.test.ts` reads both files directly (no `skipIf`, since the fixture is now committed with the slice — a missing file fails the test, it never silently skips) and asserts `markerUnchanged === true` plus a rejection-shaped string present in the raw stream.

D14 status, round 1 (2026-09-27, superseded by round 2 and later below — kept for history only): codex now runs isolated (`--ignore-user-config`, `--skip-git-repo-check`, the eight `--disable` features above, a minimal env allow-list, a fresh empty per-run directory) and `describe()` reports `enabled: false` unless `providers.codex.allowReadOnlyShell: true` is set, with `run()` refusing `provider_disabled` while unset — per the parent spec's D14 exception text (user decision 2026-09-27). The shell/exec tool itself is still reachable under `-s read-only` even when enabled; this is the accepted, documented exception, not a closed gap.

D14 status, final for v1 (superseded by the round above, kept for history): the codex shell/exec tool is still reachable under `-s read-only` (restricted, not removed — an accepted, documented gap, not claimed closed); the `wowc` MCP server's own tools are read-only by contract and now auto-approved via `default_tools_approval_mode="approve"`, which does not touch the shell tool's approval requirements. `provider.codex.stream` asserts the completed tool call, its `failure` field is `undefined`, and the raw fixture carries the `WOWC_RUN` echo proving env propagation.

Web search, live probe (2026-09-29, PM machine, recorded by the PM, not by a builder): codex run through the adapter's shipped argv, which carries `-c web_search="disabled"`, was asked to use the web; it answered `NO_WEB_TOOL` and the stream held no web item. The control run without `-c web_search="disabled"` performed a `web_search` and fetched wowhead, so this config key is what removes the web tool (`web__run` in `no-shell-probe.txt` is the same tool). `provider.codex.web` in `provider.codex.test.ts` pins the flag in the argv of every run.
